# Project Write-Up

## Design decisions

**Single orchestrator over multi-agent.** A customer service query for a telecom provider follows a fixed sequential path: classify the intent, decide on a routing action, execute the relevant tools or retrieval, escalate if needed, reply. Each state depends on the previous state's output, so there is no structural parallelism to exploit. A multi-agent architecture would add coordination overhead and inter-agent communication surface without reducing latency or improving quality. The state machine also makes the system straightforward to test: each state has well-defined inputs and outputs, RouteState is covered exhaustively with pure-Python unit tests, and ActState tool calls run against local fixture data. If requirements change and parallel data retrieval becomes necessary, the natural extension point is ActState itself, not the top-level orchestration model.

**Deterministic routing over LLM routing.** RouteState is pure Python. It applies a small set of priority rules to a structured `ClassifyOutput` and adds effectively zero latency. This was a deliberate choice, not a shortcut. Routing is policy, and policy must be auditable: the conditions under which a query reaches a human agent have to be traceable without running an inference call. The most critical rule is that `escalate` intent routes to `SKIP_TO_ESCALATE` before the confidence gate, so a low-confidence injection attempt still reaches a human rather than being deflected into a clarifying question. Off-topic detection outranks it, so an injection also flagged `off_topic` is refused instead; neither path complies with it. That determinism disappears the moment routing is delegated to a model. Deterministic routing also means RouteState has exhaustive unit test coverage without a single LLM mock, which runs in milliseconds and never flakes.

**Azure AI Foundry Agents over direct Chat Completions.** Foundry's built-in `file_search` tool eliminated the need for a custom RAG implementation: vector store indexing, retrieval, and content safety filtering are handled by the platform. Tracing comes out of the box. The cost is the polling model: each agent run requires at minimum four HTTP round trips (create thread, post message, start run, poll until complete, fetch response), and two to three sequential runs per query puts p95 latency between 14.5 and 18.5 seconds across measured runs. That is an architectural constraint, not a tunable parameter. If sub-5s p95 were a hard requirement, the right choice would be streaming Chat Completions for the non-retrieval agents (Classify, Escalate, Respond) with a separate vector search step for INFO_PATH. I would make that tradeoff in production; Foundry works well for prototyping and for a system where latency is acknowledged rather than disguised.

**DataSource abstraction for billing.** `get_billing_info` reads billing records through a `BillingDataSource` Protocol rather than directly from a file. Two implementations exist: `JSONBillingDataSource` for local development and `SQLiteBillingDataSource` for the seeded relational database. The Protocol imposes no inheritance requirement on implementations, so adding a third (a real billing API, for example) means implementing one method and setting a config value, with no changes to `get_billing_info`, its callers, or its tests. I applied this pattern only to billing because it was the tool with the most data access complexity, but the same approach applies to any tool reading from an external system.

## Tradeoffs made

**Latency vs. reliability.** Synchronous sequential Foundry polling is predictable: each state waits for the previous one to complete, errors surface immediately, and the pipeline never gets into a partial-success state where some agents have run and others have not. The cost is a p95 of 14.5 to 18.5s across runs, about three times the 5-second target. Achieving that target would require replacing the polling-based Foundry agents with streaming Chat Completions, adding a separate vector search step for INFO_PATH, and accepting more complex state management in exchange for lower latency. That is a significant architectural change. For a demo and evaluation system, synchronous polling is the right tradeoff; for production, the latency is a known blocker documented as a structural constraint, not an optimization opportunity.

**Deterministic tool dispatch vs. flexible LLM tool choice.** ActState routes each decision to a fixed Python function: BILLING_PATH calls `get_billing_info`, TECHNICAL_PATH calls `get_customer_account`, `check_network_outage`, and `run_speed_diagnostic` in sequence, and so on. Within each path the tools are determined by the routing decision, not by the model. This eliminates within-path tool selection errors entirely, but it caps the tool selection metric by construction. The technical path fires all three tools on every technical query while most golden rows expect only the one the question calls for, so those rows score 0.5 for extra-but-correct calls. In run 5 (2026-08-23 18:02) 17 rows were capped this way, putting the maximum achievable score at (100 - 17*0.5)/100 = 91.5% before any genuine error is counted. Misclassification is the smaller contributor, explaining 9 of the 27 sub-1.0 rows. The ceiling is a property of fixed dispatch rather than classifier quality, and lifting it requires either conditional tool invocation or golden labels that accept the designed sequence. The alternative, giving the act agent free choice over all tools, would add variance and make the system harder to test; the current approach trades flexibility for predictability.

**Bypassing RespondState for billing.** When `get_billing_info` returns successfully, `state_machine.py` short-circuits RespondState and returns the pre-formatted billing reply directly. This guarantees correct number formatting (the `_fmt` helper in `_format_billing_outputs` handles negative values and two decimal places consistently) and removes a hallucination surface where the respond agent might restate dollar amounts in a different format. The billing bypass hardcodes the response template, which solves currency formatting reliably but means the respond agent never sees billing queries in production; the eval and production paths diverge on one of the most common query types.

## Failure cases and what we learned

**SDK API changes broke integration earlier than expected.** During early implementation, tests were written against mocked interfaces that matched documentation rather than the installed SDK version. When the tests ran against the real Azure AI Agents client, several method names had changed: the threading and message APIs had moved to sub-clients, and `MessageRole.ASSISTANT` had been replaced by `MessageRole.AGENT`. The fix was straightforward once identified, but the lesson is that SDK method names should be verified against the installed package version before tests are written, and at least one integration test should run against the real client per agent type, even if the rest of the suite uses mocks.

**Eval contamination made the initial baseline untrustworthy.** During Phase 2.11 optimization, six verbatim queries from the golden set were included in `CLASSIFIER_SYSTEM_PROMPT` as boundary rule examples. Any accuracy measured against that prompt was partly measuring memorization rather than generalization, so the number could not be trusted in either direction. When we identified the contamination and replaced the examples with uncontaminated paraphrases, accuracy rose from 86% to 88%: the verbatim examples had not been helping. The contamination cost confidence in the measurement rather than inflating it, which is a milder outcome than feared and not a reason to relax the rule. The rule I would apply from the start on any future project: the golden test set is read-only once it is built. Nothing from it enters a prompt, an example, or a few-shot demonstration at any point during optimization.

**LLM agents reformat numbers regardless of instructions.** Early billing responses had the respond agent receiving raw `tool_results_json` and generating the reply. Even with explicit instructions to preserve the exact currency format, the agent would reformat `-$5.00` as `negative $5.00` or apply locale-specific conventions. Pre-formatting in Python, before the data reaches any agent, is the reliable fix. The `_fmt` helper in `_format_billing_outputs` handles the sign convention once, in one place, and the result is passed as a string the agent does not need to reinterpret. The lesson extends beyond currency: any structured data where formatting precision matters should be rendered in Python before it reaches an LLM.

## Lessons learned

- The eval framework is designed to lock KPIs before optimization begins. We discovered mid-iteration that six boundary rule examples had leaked from the golden set into the classifier prompt, requiring a re-run. The contamination was caught and fixed, but it reinforces why the golden set and the prompt must never share examples.
- Test against the real SDK as early as possible. Mocks that mirror documentation rather than the installed version give false confidence.
- Honest failure documentation is stronger than inflated metrics. The 78.6% escalation recall from the earliest runs and the p95 latency, about three times the target, are in the baseline notes with their root causes explained. That is more useful to the next engineer than a number that looks better because the methodology was softened.
- The DataSource abstraction paid for itself the first time I switched the billing backend from JSON to SQLite. Zero changes to callers, zero test changes.
- Prompt engineering has a ceiling. Classifier accuracy measured 86% with the original boundary rules, 88% after the contaminated examples were replaced with paraphrases, and 87% to 89% across the runs measured on that prompt after those paraphrases were themselves replaced with disjoint topics. Only the first of those is a prompt-engineering gain; the rest is decontamination. The remaining failures are genuinely ambiguous cases where the rules either conflict or produce regressions, and closing them requires better classification architecture, not more prompt text.
- Separating classification from routing made both independently testable. RouteState being pure Python is the design decision I would repeat without hesitation.
- Document limitations in the output schema. `verified=False` hardcoded in every escalation ticket is not a bug to fix later; it is an honest record of what the system cannot guarantee, visible to the human agent who picks up the ticket.
- The `gpt-4o` and `gpt-4o-mini` deployments retire on October 1, 2026, which is imminent. The migration path (update deployment names in `.env` before that date) is documented in [`docs/DEPLOYMENT.md`](DEPLOYMENT.md); anyone running this system needs to act on this before the deadline.
