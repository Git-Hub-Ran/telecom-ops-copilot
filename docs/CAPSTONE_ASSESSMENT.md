# Design and Operations Assessment

## 1. Why an agent instead of a deterministic workflow?

Four of the five pipeline states depend on work that cannot be reduced to deterministic logic, and ActState only partly: its billing, account, and technical paths are fixed Python dispatch, and only INFO_PATH requires synthesis. ClassifyState must map unconstrained free-text customer input to one of six intent labels; no rule set covers the vocabulary space, and the confidence score must reflect genuine uncertainty so the routing threshold is meaningful. INFO_PATH in ActState requires synthesizing an answer from retrieved knowledge base chunks whose relevance varies by query; a template cannot substitute for that synthesis. EscalateState and RespondState must generate coherent natural language tailored to the specific context of each query. The routing layer itself (RouteState) is deliberately pure Python: it applies priority rules to a structured ClassifyOutput and adds zero latency. The design separates the parts that can be deterministic (routing, tool selection per path, error handling) from the parts that cannot (intent recognition, KB synthesis, natural language generation), and uses an LLM only for the latter.

## 2. Where can the system hallucinate or make bad calls?

KB citations shown to the customer are taken from the validated act_output set, not from the respond agent, so it cannot invent or drop a doc_id. What remains unverified is whether the cited documents actually grounded the answer text: the citation is proof of retrieval, not of use, and establishing use requires grounding faithfulness, which is not computed. The respond agent on non-billing paths receives only structured metadata, not raw tool output, and may supplement with training knowledge when KB citations are thin. Account IDs are extracted from customer messages with no identity check: any user can query any account by typing a valid ID pattern, and `verified=False` is hardcoded in the escalation ticket. The escalation summary is gpt-4o free text describing the situation; it could mischaracterize the customer's issue to the human agent who picks it up.

## 3. What are the operational risks?

`gpt-4o` and `gpt-4o-mini` retire on **October 1, 2026**. Every agent in the system targets those deployments by name; without a coordinated model migration the entire pipeline stops on that date. Latency at p95 has measured 14.5 to 18.5s across the committed runs, three or more times the 5s target, and is a structural consequence of the Foundry polling architecture, not a tunable parameter. The app authenticates via Azure Device Code flow, which requires an interactive browser sign-in on every restart; a process crash in production requires manual re-authentication before service is restored. There is no rate limiting: a single user or a small script can flood the pipeline with concurrent requests, exhausting the Foundry thread quota and degrading latency for everyone.

## 4. What would break under real user load?

Streamlit `st.session_state` is in-process memory: multiple concurrent users share a single Python process, and a restart loses all session state. Each query makes one to four sequential Foundry agent runs depending on the path, each requiring four or more HTTP round trips under the polling model; there is no parallelism within a query and no connection pooling at the Foundry SDK level, so throughput is bounded by round-trip latency multiplied by the number of inflight queries. Every query creates a new Foundry thread via `client.threads.create()` with no cleanup: at scale, thread accumulation will hit Foundry project quotas. Escalation tickets are appended to a local `data/escalations.jsonl` file, which is not durable across restarts and is not readable by a separate fulfilment service.

## 5. What permissions and data access should be restricted?

The system has no customer-facing authentication: any user who can reach the Streamlit URL can query any account by typing a valid account ID, and `verified=False` is hardcoded in every escalation ticket to document this honestly. Four of the five tools are read-only lookups; `create_escalation_ticket` writes to `data/escalations.jsonl`. No tool modifies customer account data. In production, access should require an authenticated session token tied to the customer's account, and the account ID passed to tools should be derived from that token, not from the customer's message. The Foundry agents have access to the full vector store and all tool definitions regardless of the customer's query type; per-path scoping of tool access would reduce the surface area for prompt injection to trigger unintended tool calls.

## 6. How would you measure success in production?

The existing eval framework provides the starting baseline: intent accuracy >=90%, tool selection >=85%, escalation precision >=85%, and escalation recall >=80% are the targets against the 100-case golden set. In production those targets translate to sampled query audits: a 5% random sample reviewed by a support supervisor weekly, with intent and tool correctness scored against the same rubric. Latency SLOs should be set against what the Foundry polling architecture can actually deliver: across the committed runs p50 has measured 7.7 to 10.4s and p95 14.5 to 18.5s, so p50 <=12s and p95 <=22s remain honest targets, pinned above the worst observed run rather than the best; any architectural change that reduces polling round trips should be measured against these before and after. Operational health requires two additional metrics that the eval does not cover: escalation rate by intent type (a spike in info-path escalations signals KB retrieval degradation) and post-interaction customer satisfaction score (a 1-5 rating collected at session end, tracked as a rolling 7-day average against a >=4.0 target).
